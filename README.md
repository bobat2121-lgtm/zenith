# Zenith

A graded research feed for the analyst's **covered universe**: the public companies
in news-monitor's 8-minute lane (26 tickers, listed in `worker/src/covered.json`).

```
news-monitor (collection, 195 sources)
      │  read-only rowid cursor on news-monitor-db
      ▼
zenith-core Worker (Cloudflare, D1 zenith-db)
  ingest every 5 min → excerpt fetch → queue (claims with 45-min leases)
  serves the rubric, accepts grades and analyst labels, serves the feed
      ▲                                   │
      │ hourly Claude routine (grader)    │ /v1/feed, /v1/feedback
      │ grader/GRADER.md + grader/zenith.mjs
                                          ▼
                         Streamlit app (app/) — black/red X-style feed
```

## Pieces

| Path | What |
|---|---|
| `rubric/core.md`, `rubric/companies/<TICKER>.md` | The grading rubric. Bundled into the Worker at deploy (`npm run build:rubric`); its content hash is the rubric version stamped on every grade. Each sheet's front-matter `industry_links` are bundled as `INDUSTRY` (`{}` while no sheet declares one). A candidate rubric is an overlay in `rubric/candidate/` (`core.md`, `companies/<TICKER>.md`, and `BASE.json`, written only by `node scripts/build-rubric.mjs --rebase-candidate`); with one, the build adds `CANDIDATE_VERSION`, `CANDIDATE_FLOORS`, `CANDIDATE_INDUSTRY` and `CANDIDATE_SCOPE` (all null without one, and every live export unchanged). Live grading never uses the overlay; only a golden-set replay grades against it. |
| `worker/` | zenith-core: `src/ingest.js` (cursor over news-monitor-db), `src/excerpt.js` (opening text of each release), `src/index.js` (API), `src/auxiliary.js` (auxiliary names: own tables, cursor, claim, grades and feed; never touches coverage rows), `src/headlines.js` (the headline-only pass: its own lease columns, never touches grades or grading state), `src/story.js` (exact-key story dedup), `src/text-class.js` and `src/aux-text.js` (excerpt classes and the shadow auxiliary page reader), `src/replay.js` (the golden-set replay), `src/rarity.js` (the read-time rarity class), `migrations/`. |
| `grader/` | What the hourly routine runs: `GRADER.md` (procedure) and `zenith.mjs` (API CLI; `replay-claim` and `replay-submit` for the replay pass). |
| `registry/rivals.json` | Rivals declared in Zenith: `{TICKER: [{key, basis}]}`, each key a source news-monitor already polls. `scripts/sync-covered.mjs` reads it (the `rivals` option of `buildCovered`) and writes each listed source into `covered.json` as a counterparty with role `rival` and that ticker in `affects`; news-monitor's own routing is unchanged. A listed key that is not polled, is a covered company's own source, is a shadow source, is a Bing search or already has another role is skipped with a warning. It holds source keys only, never register data. |
| `app/` | Streamlit app, four pages: **Coverage Universe** (`/v1/feed`, the default), **Brief** (`/v1/brief` as data: Leads and Digests since a chosen time, waiting items, items to label, and the next 30 days from `/v1/calendar`; no model call and nothing sent anywhere), **Auxiliary Names** (`/v1/aux/feed`, every company or program outside coverage) and **Tuning** (calibration, source tuning, the grader section with held rows and the daily grading budget, and the Recall scoreboard from `/v1/recall`, counts only). The two feed pages each have a For You (Signal 60/70/80/90+, recent Leads pinned) / Latest (newest, pending included) switch, a Companies / Names filter and an Unlabeled only toggle. One-glance cards: name, source or status, score · band, age, the title as `<headline> - <tag>` (the grader's plain-language headline and item type; the original title until an item has one), the grader's one-line why, read-through chips on auxiliary cards. The Coverage page also shows a one-line source-health strip (SEC fast path, failing IR probes), an ops strip under the grader strip (news-monitor open alerts and failing managed-lane checks, `/v1/news-ops`) and a Site changes expander (`/v1/site-changes`, `/v1/source-health`). Labels High/Medium/Low/Noise and Too high/Too low, recorded against the grade on the card, plus a "why it matters" note feed back to the grader. |
| `scripts/sync-covered.mjs` | Regenerates `worker/src/covered.json` from news-monitor's lane policy, `coveredTicker` sources and every source's `role`/`affects`, `worker/src/aux-sources.json` (every other company or program source, as auxiliary names; counterparty filters built for a covered company, such as co-mention searches, FPDS feeds and Drone Dominance, are marked `coverage_subject` with the tickers they affect) and `worker/src/site-sources.json` (site-structure watchers and probes with the covered ticker each watches). `covered.json` also carries `channels` (each source's own registrable domain, used by the text class) and the rivals from `registry/rivals.json`. A source of news-monitor's register lane (a register read whole and matched on identifiers inside news-monitor) is written to `aux-sources.json` as a program entity, `coverage_subject`, with `record: true` and `register: true`. |

**Daily grading budget** (`worker/src/budget.js`, migration 0016). The arrival gate admits some rows that would once have been dropped or graded at once as *held*: `admit` set, `released_at` NULL, `state` still `pending`. The `admit` values are `record_late` (official records past the 14-day line), `seed_window` (a bounded window of a new source's first poll), `seed_fresh` (a new non-covered source's fresh seed rows), `vote` (Legistar decision rows, `#vote-<event>` or `#<status>`), `record_fresh` (an FPDS source's undated rows after its first poll), `register` (a fresh or undated row of a register source, marked `register: true` in `aux-sources.json`, after its first poll, so a register change is always graded inside the budget and never on the fast path; a late register row is `record_late`, as any record), `source_cap` (a fresh row past its source's `fast_cap` (10) fast-path rows of one first-seen UTC day, counted across both pipelines; a covered company's own sources and SEC items are never capped) and `rescue` (rows an admin rescue turned back into work, and `story_dup` copies brought back by the orphan pass or `story_release`). For a row that is neither skipped nor late, the gate decides in this order: `seed_fresh`, `vote`, `register`, `record_fresh`, `source_cap`, then the fast path. Held rows are never claimed and never counted as waiting. Every 5-minute tick releases held rows, at most 20 a UTC day across both pipelines, at most 5 per source, and only while the claimable queue of that pipeline is under 60; `seed_fresh`, `vote`, `record_fresh` and `source_cap` rows go first, then the rest (`register`, `record_late`, `seed_window` and `rescue` among them), oldest first. Override with the Worker secrets `GATE_BUDGET_TOTAL`, `GATE_BUDGET_PER_SOURCE`, `GATE_QUEUE_GUARD` and `GATE_FAST_CAP` (the per-source fast-path cap; 0 turns it off). Each news-monitor row is graded in one pipeline only.

**Story dedup** (`worker/src/story.js`, migration 0019). Before the grader sees a row, both ingests decide in code, with no model, whether it is a second copy of a story Zenith already holds. Each row gets its strongest exact key: an SEC accession, an FPDS award and modification, a Legistar matter with its fragment (a `#vote-` row is its own story), or the exact normalised title scoped by ticker (coverage) or entity (aux); auxiliary rows also get a canonical-URL key. A row that shares an exact key with an earlier live row first seen within 14 days is stored skipped with skip reason **`story_dup`**, `admit` NULL, linked to its first copy (`story_of`), when that earlier row is not held, the new row does not outrank it (a covered company's own release, then an SEC filing, then another official record, then the rest) and the new row does not bring text the earlier one lacks. When the earlier row is still held for the budget, the new row is on the fast path and the held row would pass the same tests as a copy of it, the new row is stored plain and the held row becomes its copy. A `story_dup` copy is never claimed, never takes a budget slot and is never deleted; Tuning → Left out names it as a copy of the queued story and can still force it to be graded. Arrival precedence: bad URL, key-account skip, gate skip, muted source, then `story_dup`. Register sources, official records, SEC rows and templated sources never get a title key, and register sources get no URL key either, so a register row is never held as a copy. Soft signals (fuzzy fingerprints, token sets) never hold anything. Once a UTC day, on the 00:00-00:04 tick, copies whose canonical left the queue (muted, parked, failed grading) or is missing are promoted: the earliest copy from an unmuted source becomes a held `rescue` row, at most 50 a table a day. The Worker secret `STORY_DEDUP=off` still writes the keys but holds nothing; any other value, or none, is on. `POST /v1/admin/requeue {mode: "story_release"}` is the rollback, and `/v1/ops` `backlog.story` counts the copies held.

**Excerpts and auxiliary page text** (`worker/src/text-class.js`, `worker/src/aux-text.js`, migration 0020). Each item has a text class from its source key and URL: `record` (an official record, or a government or register host), `wire` (a newswire copy of an issuer's release), `issuer` (the company's own channel, from `covered.json` `channels`) or `press` (everything else). Excerpts can be sized by class (government and register documents 8,000 characters, issuer documents and wire releases 6,000 when the article is found, third-party press 2,500), switched by `TEXT_BUDGETS=class`; unset (`legacy`, the default) every excerpt the grader sees keeps 2,500. A shadow reader for auxiliary record and issuer pages, `aux-text.js`, is built and tested (at most `AUX_TEXT_PER_TICK`, default 4, fetches a pass, one per registrable domain, never a host on its no-fetch list, no PDFs, press rows only with `AUX_TEXT_PRESS=1`; its text would go to `aux_items.page_*`, never to the excerpt), but the cron does not run it yet, so nothing is stored in `page_*`. `AUX_TEXT_SHOW` must stay 0: set to 1 it would hold every auxiliary row with no feed text out of the claim for up to 45 minutes, waiting for a page read that never runs. By default nothing the grader reads changes. Claims accept `max_chars`: the grader CLI asks for about 50,000 characters of source text per coverage claim and 30,000 per auxiliary claim, prints one "Claim limited" line when items were left for the next claim, and prints every excerpt line behind `| `, so page text can never pose as a frame line.

**Golden-set replay** (`worker/src/replay.js`, migration 0018). A replay grades a frozen set of test items under one rubric version, in the routine's idle runs only, so a rubric change can be judged before it goes live. **Golden expectations live in the private database, never in this repo**: they are loaded only through `POST /v1/admin/golden`, the replay claim never prints them, and no route returns them to the grader or the app. The admin arms a `baseline` (the live rubric) or a `candidate` (the overlay in `rubric/candidate/`) with `POST /v1/admin/replay`. GRADER.md step 7 is the replay step: only in a run where the coverage, auxiliary and headline claims all printed `NOTHING WAITING`, the grader runs `node grader/zenith.mjs replay-claim 10` once (it writes `.zenith/replay/` from the routine's checkout, and prints `NOTHING TO REPLAY` with a reason when there is nothing), grades the batch by the usual rules without labels, recent items or web reads, and submits with `replay-submit`. A replay never writes items, grades, auxiliary grades or runs, never uses the daily grading budget, makes no fetch, and its grades are never shown or used as live grades. Its own caps: `REPLAY_DAILY` (20 grades a UTC day; 0 stops every replay claim) and `REPLAY_WEEKLY` (100 in any 7 days), each overridable by a Worker secret of the same name, at most 10 items a claim and one claim a run. While a replay is armed the golden set is frozen. To the app, `GET /v1/replay` and `/v1/ops` `replay` show counts and a verdict only.

**Rarity** (`worker/src/rarity.js`). A graded row's rarity class is computed at read time from its source key and URL and never stored: `register` (an official record), `original` (a named outlet's own reporting, reached through a filter feed), `issuer` (the company's own words: SEC filings, a covered company's own lane, an outside company's own channel) or `wire` (a wire or syndication copy). It never feeds the score, the band or the claim; the grader never sees it. `GET /v1/rare` lists the rare finds (`register` and `original`); no page calls it yet.

**Universe and audit log** (D1 zenith-db, migration 0017). Every per-analyst table (`items`, `aux_items`, `grades`, `aux_grades`, `feedback`, `aux_feedback`, `source_prefs`, `expansion_candidates`, `recall_events`, `deliveries`, `reports`) carries `universe_id`, always `u1` today. `audit_log` is append-only (triggers refuse UPDATE and DELETE): the Worker writes one row per human or token action that changes state (labels, source preferences, Left out grade, expansion decisions, requeue and rescue, recall loads, admin runs, admin grade submits), after the action succeeds, holding ids, labels, statuses and counts, never note or event text; grader submits and cron work are not logged. Read it with `cd worker && npx wrangler d1 execute zenith-db --remote --command "SELECT at, via, action, target_kind, target_id FROM audit_log ORDER BY id DESC LIMIT 20"`.
